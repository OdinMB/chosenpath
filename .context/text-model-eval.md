# Text models: settings, call logs, and the text-model eval

## Production text calls

- **One factory.** Every text `ChatOpenAI` comes from `createChatModel` in `server/src/shared/llm/chatModel.ts`. Don't construct `ChatOpenAI` anywhere else.
- **Production runs GPT-6 only** (migration of 2026-09-27; nothing deployed until the owner merges). The factory still accepts two families, each with a pinned request shape, because the eval's comparison arms run gpt-4.x through it. Any other model name throws.
  - `gpt-4.1*` and `gpt-4o*` send `temperature`, and an output cap as `max_tokens`. Eval only.
  - `gpt-6-*` and `gpt-6.1-*` (GPT-6.1 Sol, released 2026-09-29, accepted since 2026-09-30 and no group's default; a later point release is refused until its page is read) never send temperature. They always send `reasoning_effort` (none, low, medium or high, each model at the efforts it takes: `reasoningEffortsFor` in `textModelSettings.ts`, where `gpt-6.1-sol` takes no `none`, per OpenAI's model page; `minimal` is rejected everywhere) and `prompt_cache_options: { mode: "explicit" }`, and in production an output cap as `max_completion_tokens` (which counts reasoning tokens), all through `modelKwargs`. LangChain 0.6.7 does not recognise gpt-6 as a reasoning model, so its own `maxTokens` would go out as `max_tokens`. The filter check of 2026-09-27 confirmed that GPT-6 accepts `max_completion_tokens` this way.
  - Structured output stays on the default strict `json_schema`.
- **Per-role settings** live in `server/src/shared/llm/textModelSettings.ts` (`TEXT_MODEL_GROUPS`). `productionTextModels()` in `server/src/config.ts` resolves them on first use and logs one `[LLM] text models {…}` line with every group's `model@effort`. `server/src/index.ts` calls it before anything listens, and the routes build the content filter on import, so a bad setting stops the server at startup. It is lazy so the eval, which imports `config.ts` for its storage paths, never reads production's model env. Each group reads `_NAME` and `_REASONING_EFFORT` from its own prefix and nothing else. An empty value counts as unset.

  | Group | Env prefix | Default (2026-09-27) |
  |---|---|---|
  | Custom-story setup | `SETUP_MODEL_*` | gpt-6-luna, low |
  | Template editor (AI Draft, AI Iteration) | `GENERATION_MODEL_*` | gpt-6-sol, low (since 2026-09-28) |
  | Single-player beats | `TEXT_MODEL_*` | gpt-6-luna, medium |
  | Multiplayer beats | `MULTIPLAYER_TEXT_MODEL_*` | gpt-6-luna, low |
  | Single-player switch and thread analysis | `SWITCH_THREAD_MODEL_*` | gpt-6-luna, low |
  | Multiplayer switch and thread analysis | `MULTIPLAYER_SWITCH_THREAD_MODEL_*` | gpt-6-luna, low |
  | Content filter | `CONTENT_FILTER_MODEL_*` | gpt-6-luna, low |

  - Why these: single-player turns on Luna medium; multiplayer turns on Luna low, because Luna medium's 3-player p95 was 62 s, over the 60 s cap; setup on Luna low, the only GPT-6 arm inside the setup wait cap, rated on par with gpt-4.1; templates and AI Iteration on Sol low since 2026-09-28 (the owner's templates page, round 1 as it ran: Sol better on 3 items, the same on 6, worse on none, the repeat agreeing; no player waits on it, and its timeout was sized for Sol: 150 s, raised to 240 s on 2026-09-29 after the final check's slow evening); analysis on Luna low; the filter on Luna low after the filter check (`.context/content-safety.md`).
  - A gpt-4.x `_NAME` stops the server with the variable and its replacement, for example `TEXT_MODEL_NAME=gpt-4.1-mini: gpt-4.x models no longer run production text calls (GPT-6 migration, 2026-09-27). Set TEXT_MODEL_NAME=gpt-6-luna and TEXT_MODEL_REASONING_EFFORT=medium, or remove TEXT_MODEL_NAME to use that default.` Any other non-gpt-6 name stops it too.
  - `_NAME` unset: the group's default model at its default effort, or at `_REASONING_EFFORT` when that is set. `_NAME` set: `_REASONING_EFFORT` must be set too. An effort outside none/low/medium/high stops the server; the gpt-4-era `minimal` gets its own hint. So does an effort the model does not take, since OpenAI refuses it (a 400, never retried): `GENERATION_MODEL_REASONING_EFFORT=none is not supported by gpt-6.1-sol, which takes low, medium or high: … Set GENERATION_MODEL_REASONING_EFFORT=low.` The factory's `assertSupportedSettings` refuses the same settings, so the eval can't send them through production's path either (the probe sends refused shapes as raw bodies).
  - `_TEMPERATURE` is ignored with one warning per variable.
  - Setup no longer falls back to `GENERATION_MODEL_*`, and the multiplayer groups no longer inherit the single-player ones: templates can move to Sol without taking custom-story setup along, and multiplayer turns keep their own effort.
- **Retries, timeouts and output caps.** Every production call retries at most twice (`PRODUCTION_MAX_RETRIES`), and each retry is logged. A custom `onFailedAttempt` replaces LangChain's default policy, so `retryHandler` re-applies it: no retry on 400–409, cancel/abort or `insufficient_quota`. A malformed JSON reply, and a reply cut at the output cap (`finish_reason: length`, which leaves unclosed JSON), fail inside LangChain's retried section, so they are retried too. `productionCallLimits(role, players)` in `chatModel.ts` gives each role's timeout and output cap; `AIStoryGenerator` passes the story's player count, `ContentFilterService` one player. The values and their derivation are under "Timeouts and output caps" below.

## Call and turn logs (no text, no user ids)

- **`[LLM] {…}`** comes from `llmCallLogger` in `server/src/shared/llm/usageRecorder.ts`, one line per call. It carries:
  - role, model and effort;
  - `metrics`: input, cached, cache-write, output and reasoning tokens, finish reason, a refusal flag, the served model and the service tier;
  - `ms`, and `error` {name, status, code, param, finishReason} on failure;
  - the invoke tags: storyId, turn (the turn being generated), players, beatType (beats only), images and pregeneration.

  Only these tag names pass (`tagsFrom`); any other metadata is dropped. The factory puts `role` into the model's metadata, and callers pass the story tags as `invoke(prompt, { metadata })`.
- **`[LLM] retry {…}`** is one line per retry: role, attempt, retriesLeft, status, code, name and finishReason.
  - A reply cut off at its output cap never reaches `metrics.finishReason`: with strict structured output, openai's parse throws `LengthFinishReasonError` before LangChain sees the reply, and the call is retried. So it shows only as `"finishReason":"length"` on the retry line, or in `error` when every attempt was cut off (`errorFinishReason`; `content_filter` likewise).
  - `name` is the error's class where its name is the generic "Error" (`errorName`): openai's errors set none, so a 500 reads `InternalServerError`, a cut-off reply `LengthFinishReasonError`, a timeout LangChain's `TimeoutError`. No error message is logged, since some quote the model's reply.
- **`[LLM] text models {…}`** is one line at startup: every settings group as `model@effort`, as resolved from env (`describeTextModels`). It is the first thing to check after a deploy.
- **`[TurnTiming] {…}`** comes from `server/src/game/services/turnTimings.ts`, which keeps in-memory timestamps for at most 5,000 stories. It logs three events:
  - `delivered`, with the wait since that story's last choice. It fires only when a broadcast carries a higher turn; choice and image broadcasts don't count.
  - `choice`: reading seconds (only for a choice on the delivered turn), pregeneration `complete`/`partial`/`none`, and `duplicate`. `duplicate` means the pregeneration was not complete and still running, so the live progression repeats it.
  - `pregeneration`: seconds and ok.
- Retention is the host's log retention.

**Runner.**
- Transport failures (429, 5xx, timeouts, dropped connections) retry after a backoff, on their own budget of 3. A 429 whose code is `credit_balance_exhausted` or `insufficient_quota` is never retried and leaves its job open (`NEVER_RETRY_CODES`, `finishesJob`, since 2026-09-29): it says nothing about the model, and the next invocation sends it once the account has credit.
- A reply production's LangChain parse rejects is re-sent at once, at most `PRODUCTION_MAX_RETRIES` (2) times, as production does. That covers `repaired` (text after the JSON), `invalid-json`, `schema-mismatch`, `length` and `refusal`.
- A 400 is never retried. One naming a parameter (`rejectedParam`) leaves its job open: the next invocation plans it again. `finishesJob` in `runner.ts` is the one definition of finished, used for resuming, for case building (`finishingRecord`) and for the variant section's pairs. Validity, the call count, the cost and input-cost means and the cache readings leave such attempts out, like transport failures, and the rejected-parameter rate still reads over all records. So a request-shape bug found by a smoke run leaves no dead job, and a job still waiting for its re-run is neither a matched pair nor a $0 call.
- **Production's one checked retry of a turn** (`CheckedRetry` in `runner.ts`, `checkedRetry` in `jobPlan.ts`, since 2026-09-30): a turn job of a stage `stageChecksTurns` names (only `choice-line-sp`) carries production's check and retry (`checkedBeatReply`, `beatChecks.ts`). Where the first reply as parsed is one short paragraph or has no options (`beatReplyProblem`, with the ending's flag), the runner sends the retry right after it as the job's step 2, the first request told the problem (`withBeatProblem`), on the same arm, schema and limits, with production's parse re-sends inside it. The first reply's final record then carries `checkedRetry` (`short`, `noOptions` or `both`) and does not end the job; the retry's records carry it too, and its final record ends the job. A job whose retry is due but unrecorded (an interrupted run) is open, and sends step 1 again on the next invocation. The generic readings read a turn by its first reply: `isResultRecord` and the turn waits leave a turn's step 2 out (`isCheckedRetry`), a first reply the retry follows is a finished pair (`finishesFirstReply`), and an arm's prose counts it once; the reply the game keeps, the wait including the retry and the cost are the checked-turn report's (`--choice-line-sp`, above).
- Every attempt is a record in `calls.jsonl`. Attempts are numbered after those already recorded for the job and step, so a re-run (a re-planned rejected request, or a job resumed part-way) gets new callIds and never overwrites an earlier attempt's `outputs/<callId>.json`.
