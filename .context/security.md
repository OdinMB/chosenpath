- **Authentication**: JWT tokens with secure cookie handling
- **World edit access**: these routes take a signed-in account (`verifyUser()`, else 401) with edit access to the World they change (`ensureTemplateEditAccess()` in `server/src/templates/templateMiddleware.ts`, else 403; 404 for an unknown World): its creator, or an account with `templates_edit_all` (admins).
  - Saving, deleting and iterating a World, and uploading its files (`server/src/templates/templateRoutes.ts`, by the route's `:id`).
  - Renaming or deleting its element images (`server/src/images/imageRoutes.ts`, by the route's `:id`).
  - Generating its element, player and cover images (`server/src/images/imageGenerationRoutes.ts`, by the body's `templateId`; they also need `templates_images`). Their World, element, player and reference ids must pass `validateSafePaths()` (`server/src/shared/safePaths.ts`, else 400), and both checks run before the request is screened or an image is generated.

  The GET routes that serve images stay public.
- **CSRF protection**: double-submit token (`server/src/shared/csrf.ts`). The server sets a random `XSRF-TOKEN` cookie the client can read, and answers any request other than GET, HEAD or OPTIONS whose `X-CSRF-TOKEN` header doesn't match it with a 403 `{ status: "error", errorMessage: CSRF_FAILURE_MESSAGE }` (`core/types/api.ts`), which echoes nothing from the request. Its log line names the method, path and which check failed, never a token or cookie. The client (`client/src/shared/apiClient.ts`) recognises that 403, re-reads the cookie (the rejection sets a fresh one when the browser had none) and retries once if the token changed; otherwise the pop-up asks for a reload. Neither side logs token values.
- **Client address**: one function for HTTP and Socket.IO (`server/src/shared/clientAddress.ts`). The visitor is the `TRUST_PROXY`-th `X-Forwarded-For` entry from the right (`.context/deployment.md`, "Client address (`TRUST_PROXY`)"), never the leftmost entry or the socket. An address that can't be read (no header, a chain shorter than the count, an entry that is no address) is UNKNOWN, and all such requests share one bucket; the server counts every address read and how many found none, since start and over the last hour (`server/src/shared/unreadableAddresses.ts`, counts only). `/admin/system` shows them beside the verdict, and the log warns with those counts at most every ten minutes while unreadable reads come in, never with an address or header. An IPv6 address counts by its /64 network (`addressKey`), which one connection usually holds whole. With `TRUST_PROXY` unset (legacy mode) it takes the leftmost entry, or the socket when that is no address, as the app did before; a visitor can forge it, and the server warns at startup.
- **Rate limiting**: in-memory fixed windows per key and action (`server/src/shared/rateLimiter.ts`, `RATE_LIMITS` in `core/config.ts`). A request is counted when it is let through, before anything is awaited (`claimRateLimit`), so parallel requests meet the same cap as sequential ones. A request that turns out not to count hands its count back: a success where only failures count, a sign-up that created no account, a start refused by the spend ceiling, or a World start that creation refused. A key is an address, an account or a story seat, and the kinds never share a count. Who is counted for what is `server/src/shared/limitPolicy.ts`:
  - Anonymous story starts: per address, `initialize_story` 2 per 30 min, with images or not.
  - Signed-in story starts: per account, `initialize_story_text` 15 per hour without images, `initialize_story_images` 2 per 30 min with them.
  - Choices, character picks and turn retries: per seat in a story an account started, otherwise per address (an anonymous story, no seat, or an origin that can't be read), `make_choice` 4 per 30 s. The story's origin is remembered per story for ten minutes (`server/src/stories/storyOrigins.ts`), and dropped at once when this server deletes the account that started it.
  - Sign-up: per address, `register` 3 per 24 h, counted only when an account is created.
  - Code checks: per address, `verify_code` 15 per minute, counting failures only (`limitFailures`): the socket's `verify_code` and `rejoin_session`, and `GET /stories/:code/exists`. A class joining from one address with valid codes is never limited; someone guessing codes is.
  - Login: per address, `login` 20 failed logins per 15 min; a successful login doesn't count, and over the limit the password isn't checked.
  - The template editor's AI and image routes: per address, checked before the call and counted after it.

  Limiter log lines name the key's kind and the action, never the key, so no address or account id reaches the logs.
- **Daily spend ceilings**: `server/src/spend/spendLedger.ts` books every AI call's cost to its story's origin (`anonymous` or `account`), or to `other` for calls tied to no story, in `spend_daily` (`.context/storage.md`). Once today's spend in a bucket reaches its ceiling (`.context/deployment.md`, "Daily spend ceilings"), new stories of that kind get a 503 `SPEND_CEILING_MESSAGE` (`core/types/api.ts`) and running ones get no new images. It fails open: a ledger that can't be read lets requests through, and recording never throws into a model call.
- **Input validation**: Zod schemas validate all inputs
