### To manipulate and get information from the StoryState, use model classes

- Relevant model classes include Story.ts and ClientStateManager.ts, PlayerManager.ts, and ThreadManager.ts (all in shared/models directory).
- If these classes don't yet have a function to manipulate or get the required information from StoryState, add new functions to the classes.
- Don't add any complicated StoryState browsing and manipulation logic in other parts of the app.
- Keep story manipulation logic centralized in these domain models

### Checks and repairs on model replies

The game keeps what a model reply means, not only what matches an id exactly. Each repair is a `Repair` record (`server/src/game/services/textRepairs.ts`); `logRepairs` prints one `[LLM] repair` line per reply with the role, story id, turn and the count per kind (notes apart). The line carries no story text and no model-written ids; the records do, for tests and the eval, which checks replies after these repairs and counts them per kind (`.context/text-model-eval.md`, "Checks on what the game keeps").

**Beat replies** (`server/src/game/services/beatRepairs.ts`, `repairBeatReply`). `AIStoryGenerator.generateBeats` runs it on every reply, pregeneration siblings included, before `beatStep.apply`, so the beats are stored already repaired. `ChangeService` still applies exact ids only.

- Stat changes: a player stat in seat form (`player1_energy`, `player_player_energy`) is read as the plain id under that seat; a shared stat under a player moves to `shared`; in single player every player-stat change goes to player1. A player stat under `shared` in multiplayer, or a seat form under another player's group, is ambiguous and dropped; unknown stats are dropped. Both are counted.
- A `setString` on a number, percentage or opposites stat whose text reads as one value (read as a background value is: `"a|b"` summing to 100 is a, `"40%"` is 40, `"12"` is 12) becomes the `setNumber` the game applies (`statNumberAsText`). ChangeService drops a text on those types, so before this a switch turn that moved a contest's scoreboard as `setString "35|65"` left the score at 50 (setup round 3's chain). A signed value (`"-10%"`, `"+5"`, or a number below 0) is a change by so much, not a value to set, and is left as it was (ChangeService drops it); read as a value it would set health to 0 or gold to 5.
- A `setString` value its stat's non-blank `possibleValues` don't mention is a note (`offLadderValue`); the change still applies.
- A contest's scoreboard moves only toward the side that won the contest step or chapter the turn follows (`scoreboardDirection`, since 2026-09-30; `scoreboards.ts`). The scoreboard is the shared opposites stat the contested outcome's resonance names ("Scored by …"): setup round 3's form (production since 2026-09-28), which also puts player1's side (with three players, player1's camp) first, so its value is that side's share and up is toward it. Only a contest with player1 on side A is read (the plan check's PL-11 puts them there when they are in it). Left as written: a story set up before round 3, which names no scoreboard and whose opposites stats were meters for what changes often, with either side first (the old fallback to the story's one shared opposites stat turned correct moves around on those); and a contest player1 sits out, whose sides are the planner's and whose camp no check reads. The result followed: at a switch or the ending, the chapter that just ended (`getResolvedThreadAnalysis`); in a chapter, the step just played (none on its first step). A move the other way is turned around by the same size (an addition becomes a subtraction and back; a value set is reflected around the score before, within 0 to 100): the model sized the move, the recorded result says which way. Moves are read in order, each from the score the ones before it leave, after the `statNumberAsText` repair. After a mixed result, where two contests on one scoreboard disagree (or one of them is not read), and on turns that follow no contest result, moves stay as written (the setup's rule moves a scoreboard only after a thread about its contest, none after a mixed result, which this doesn't enforce). A contest turned into one side's challenge (PL-12) is not read: which side its players are on isn't stored. Found by the playthroughs (food trucks turn 22: after side B's win the reply's own reasoning said "15 points toward" side B and it wrote `addNumber 15`, 35|65 → 50|50).
- Stat bonuses (`modifiersToSuccessRate`, on every challenge option, the ending's too): an id `Story.getStatById` already resolves is kept (the exact id, a shared stat, or the seat form `player1_energy` the bonus contract asks for). One it doesn't (the doubled `player1_player_skills_traits` or `player_player_skills_traits`, which GPT-6 wrote for 14-20% of counted bonuses; a seat on a stat whose id has no `player_`) is read as the stat changes' seat form is and written as the contract asks, `player1_skills_traits` (`bonusStatIdSeatForm`), or as the plain id where the stat's id has no `player_` to replace, so the roll breakdown players see names the stat instead of showing the raw id. The seat is the option's own; in single player every seat is the one player's. In multiplayer another player's seat is ambiguous (`bonusStatAmbiguous`) and a seat the story lacks unknown (`bonusStatUnknown`), and so is anything else unresolved: those stay as written and are notes, since the game counts a bonus's points whatever its id.
- Facts: kept on `world`, a story element or an element created in the same reply. A fact filed under a stat, an outcome or a player slot becomes a world fact prefixed with the stat's name, the outcome's question or the character's name; any other id becomes an unprefixed world fact.
- Introductions of an element that neither exists nor is created in the reply are dropped.
- Milestones: the group comes from the outcome (shared first; an id held in two lists is noted). An unknown id is mapped only when exactly one ended thread's outcome has no milestone in the reply and exactly one milestone has an unknown id; otherwise it is dropped. Only what was played gets a milestone (`milestoneNotPlayed`, the owner's decision of 2026-10-01: "The idea was -not- for the engine to invent missing milestones for open outcomes. Unfinished outcomes should be narrated as unfinished. Only what was played."): each outcome keeps as many of the reply's milestones, the first written, as threads of the chapter that just ended pushed it, and no other outcome gets one, unfinished or complete, at a switch and at the ending alike; a turn that ends no chapter keeps none. Until then a milestone on a known outcome no ended chapter pushed was kept (TR-4): the second playthroughs' estate agents' ending added one to each of four complete outcomes beside the last chapter's, the only such milestones in either round's stored runs (`playthroughReplay.test.ts`). On turns that may add milestones (`canAddMilestones` in `storyTextSteps.ts`: the ending, or a switch after the first beat), an ended thread (`Story.getResolvedThreadAnalysis()`) whose outcome got fewer milestones than threads that pushed it gets its planned `thread.milestone`; exploration threads record theirs too (`ThreadResolutionService.getMilestone`).
- In a group turn, a sacrifice or reward that draws on a shared stat goes to one player per turn (`sharedLeverRepeated`, since 2026-09-30): the first seat offered it keeps it, and each later seat's copy of the same lever (sacrifice or reward) on the same stat leaves that player's options, so they choose from two. An option names its lever's stat only in its text, so the stat is read as the eval's lever readings read it: the stats the text names (a plural name also without its "s"), else those whose held value it names ("Ivo Senn" in the crew's Dockside Favors), else the one stat that allows that lever; of those, the ones that allow it; none unless exactly one is left, and then nothing changes (`leverStatOf` in `leverPayments.ts`). Only in a challenge set: in an exploration set an option's position is its result, so the copy stays and is noted (`sharedLeverRepeatedKept`). A lever on a player's own stat is every player's own, and a sacrifice and a reward of one stat are different levers. Found by the playthroughs (space pirates turn 16: "Call in Ivo Senn's dockside favor" offered to two players in one shared challenge, the crew's one favour; both took its +30).
- A sacrifice or reward is charged once (`leverChargedAgain`, since the review of the second playthroughs, 2026-09-30; `leverPayments.ts`). A lever is paid only through the next reply's stat changes, so `beatStep.apply` records on each chooser's new beat the lever that turn paid (`Beat.paidLever`: kind, the stat's group and id, and the step that paid it, -15 for 60 → 45; the first change that moves the lever's stat its way, `leverDirection`: as the chosen option's words about the stat say ("rise", "lower", "+10%", "spend" …), else as the stat's own lever rule's words about it say, else a sacrifice down and a reward up, since setups write a sacrifice on a stat where more is worse as a rise (`LEVER_DIRECTION_LINE` in the setup's stat rules and the lever fields' first sentences, `SACRIFICE_FIRST_SENTENCE` and `REWARD_FIRST_SENTENCE` in `setupSchema.ts`, adopted 2026-10-01 from the lever-direction stage: "Let Suspicion rise 10% …", "Lower Suspicion 10% …"; the turn's own lines still say a sacrifice loses what was sacrificed, unmeasured with a rising one). A word speaks of the stat only within two words of its name (or a word of it, "stability") or one of an unsigned amount, and a word that acts on the stat or compares an amount of it ("spend", "gain", "more", "less") only before it, a signed amount only right beside the name; so "10% harmony to gain a boost", "credits … so more delegates can stay" and a rule's "+30 bonus" say nothing (the first reading, of every word in the text, had such words turn an ordinary stat's sacrifice into a rise, so its correct payment went unrecorded); percentage and number stats only, a list's or a ladder's payment has no size a repeat could match; the lever's stat read from the option's text as above). On the turn after, the beat repairs drop the first change that moves the same stat by the same step, one per payment. Kept: a charge a lever chosen on the last beat now owes (any player's, same kind, same stat), a change of another size or the other way, a late payment (a last beat that recorded none), and every later turn. A change of the same size a stat's own rule happens to ask for on that very turn is dropped too; none showed in the stored playthroughs (round 2 whole, round 1 as far as it replays), where the repair drops exactly round 2's two double charges and nothing in round 1 (`playthroughReplay.test.ts`). Found by the second playthroughs: the paying turn narrates the cost, and the next reply read it as still owed (New Avalon turn 4: "Jun spent 15% of his reserve bracing the control ring", 45 → 30 a turn after 60 → 45; the mouse story's ending: "Bran used a Pantry Crumb as a wedge in the previous beat", 2 → 1). The request itself is unchanged: telling the next turn the lever is paid would be a measured prompt change.
- Option types follow the player's phase (`expectedOptionType`): exploration at switches and in exploration threads, challenge in challenge and contest threads; the ending is untouched. A converted challenge option gets risk "normal", no bonuses, and base 0, or the fixed sacrifice / reward points.

**The planners (planner v2, since 2026-09-28).** The switch and chapter planners write lean replies (`plannerReplies.ts`), which the request's `assemble` turns into the stored `SwitchAnalysis` / `ThreadAnalysis` before the plan check and the story read them. A topic direction is a sentence plus the one outcome it pushes (from the story's outcome ids as a list), stored as today's `"text (outcome id)"` string with the pair beside it (`topicDirections`); the player's pick sets the next chapter's outcome in code (`pacing.ts`, `pickedOutcome`: a flavor switch's outcome, or the chosen direction's by position), so a single player's chapter plan writes no outcome; a group's plan names it, from the ids as a list, and the plan check holds it. When a single player's pick names no outcome the story knows (the switch turn always offers three options, so a switch planned with two directions gets an invented third; or a switch planned before planner v2 whose chosen direction names no id), the chapter takes a fallback (`fallbackOutcomeId`: the outcome that still needs the most milestones, the main outcome on a tie, then the first listed), which PLAYER DECISIONS and PACING name and the assembly stores; the plan check notes it (`chapterOutcomeFallback`). Without it the reply, which has no outcome field, would fail the check on both attempts and stop the story at that switch. Both planners read a PACING block the game computes (`pacing.ts`: turns left, threads that fit (turns left ÷ 4, and since 2026-09-30 never fewer than the length rule makes come, `fewestThreads`: at 3 turns left "about 0 more threads fit" had stood beside "exactly 2 beats"), milestones still needed with the ended chapter pending, complete outcomes, the main outcome, recent lengths, the phase, and for the chapter planner the lengths allowed and the last chapter); priority is binding late in the story (the owner's call). A chapter carries its kind, question and plan beside today's fields. Since the owner's feedback of 2026-09-28 (planner v2c) the chapter's question is nearer than its outcome's (its three milestones answer it, about the chapter's own situation: a place, a person, a deadline, an object; never the outcome's question reworded, and a topic switch's chosen direction is narrowed to it too, since a direction can restate its outcome), and the planner writes the kind of milestone itself (`typeOfMilestone`, the concrete thing the answer settles; the question stands in where a reply leaves it empty). Since 2026-09-30 (planner v2e, the owner's feedback of 2026-09-29 and decision of 2026-09-30) the chapter names its outcome's stages (`outcomeStages`, one per intended milestone, stored on the thread and read by nothing yet) and stays within the one PACING says it settles: an outcome with n intended milestones has n stages, and the chapter settles stage k = milestones so far + 1 (`stageOf` in `pacing.ts`; none once the outcome is complete, when the chapter is an aftermath), so a story saved mid-story reads its stage from the milestones it holds. The story's last chapter settles only its outcome's next stage too, never the whole outcome at once, and the ending tells each outcome as its milestones leave it (the owner's decision, production since 2026-09-30: `ENDING_OUTCOME_RULE` and `ENDING_OUTCOME_KINDS` in `BeatPromptService.ts`, with each outcome's standing after the ending's milestones from `endingStates.ts`, complete or unfinished, k of n, counting one milestone per resolved thread on the outcome, which the state's "Milestones (k / n)" leaves out; a complete outcome resolved as its milestones point, an unfinished one in its current state, even if inconclusive, never beyond its milestones, in the story's own words). Since the owner's decision of 2026-10-01 ("Only what was played") the ending tells an unfinished outcome as unfinished, the story ending with it still open (`ENDING_OUTCOME_KINDS`, the current-state rule word for word), and its milestone lines say that only the threads that just ended get milestones, none on any other outcome (`ENDING_MILESTONES_PLAYED`); the beat repairs drop any other (`milestoneNotPlayed`, above). Unmeasured, a settled decision; the kept tests log it (`withEndingOnlyPlayed`). The reply lists each step once (the steps before the last, then the last step alone): planners had written the last step twice, making a chapter a beat longer. Since the choice-result stage of 2026-09-30 (planner v2f) each step result follows a rule for its kind. A challenge or contest result, the milestones included, says how the attempt turns out (what the player or each side achieves or fails to achieve, and how others respond), never which approach the player takes or what they say or decide: the result is rolled against the option the player chose, and a result that names an action had the next turn tell the rolled action over the chosen one (the playthroughs' New Avalon hearing chapters: "Eli plainly retracts" against "Eli defends his framing"). **The roll.** `BeatResolutionService.calculateTotalPoints` counts only the first `MAX_STAT_MODIFIERS_PER_OPTION` (2) stat bonuses, each clamped to ±`MAX_STAT_MODIFIER_POINTS` (15, `core/config.ts`); the player's point breakdown shows the clamped values, each bonus named by its stat's name (`Story.getStatById`), or by its id where no stat resolves (the beat repair above keeps that to ids it can't read). **Thread steps.** Before each thread beat, `ThreadResolutionService.resolveCurrentThreads` writes every thread's result for the beat just played. `ThreadManager.updateThreadResolution` puts it at that thread's own first unresolved step, so parallel threads each record step k on beat k and get their result and milestone on their last beat.

- **Challenge and contest steps** combine every player's roll in the thread (a challenge: the favorable rolls against the unfavorable ones set the chance of an extreme result; a contest: a tug of war between the sides' rolls), except on one player's own outcome: there, since the owner's decision of 2026-10-01 ("Yes, only count the owner's roll."), only the owner's roll decides the step when the owner is in the thread and their step has a result (`rollingSides`): a challenge's result is the owner's roll, a contest's goes the owner's side's way on a favorable roll and the other side's on an unfavorable one. A shared outcome, and a player's own outcome its owner isn't in, keep pooling; a single player, always the owner, is unchanged. Found by the second playthroughs: the estate agents' chapter 6, a group challenge on Nia's own protégé outcome, her roll unfavorable and Rory's favorable at turn 21, pooled into the mixed result her milestone recorded.
- **An exploration step** is a choice. Since 2026-09-30:
  - A thread on one player's own outcome goes the way that player chose, when they are in it.
  - Any other thread goes the way most of its players chose. A tie is broken by the game's dice (`Math.random`) among the tied choices, so a single player, the owner and a clear majority roll none.
  - Before, the first player listed decided for everyone. In a group thread on another player's outcome, player1's choice wrote that player's milestone, and the next turn narrated that player doing player1's choice (the playthroughs: 5 of 7 group exploration steps).

**Character selection.** `PlayerManager.setCharacterSelection` gives every player stat a value: a background stat the chosen background leaves out takes the stat's `initialValue` (read by type, below), or the template editor's default (`""`, `[]`, 50) when that is missing or doesn't fit. Stories already running are untouched.

**Background values by type** (`core/utils/statValueCheck.ts`). A background's starting value is checked against its stat's type: kept when it fits; converted when the reading is unambiguous (a numeric string for a number, percentage or opposites stat, percentages and opposites also as `"75%"`; `"a|b"` for opposites when a + b = 100, stored as a; a single string for a `string[]` stat, `""` as `[]`; a one-item list for a string stat); otherwise replaced by the stat's own `initialValue` read the same way, or the editor's default. A percentage or opposites value outside 0 to 100, number or string, is clamped to the range (120 becomes 100, `"-5"` becomes 0; logged as `clamped`); number stats have no range. A value whose stat id isn't a player stat (unknown, or a shared stat) is dropped. The check runs where values enter: `setCharacterSelection`, `createStoryStateFromTemplate` (story start), `StoryCreationService.generateStoryState` (a generated setup, before it is stored) and `TemplateService` create / update (a template, before it is written; ZIP imports are covered at story start). Each place logs one line with the story or template id and the counts per seat and background (`player1 background 0: 1 converted, 1 dropped`), no stat ids or values; once a place has fixed the values, the later places find nothing to log. The template editor shows the same reading as a `backgrounds` warning per background (`validateTemplateIntegrity`), saying what each value becomes; unknown stat ids stay with the existing reference error, shared stats in a background with the orphaned-stat warning.

**Story start** (`core/utils/outcomeReadiness.ts`). A story needs an outcome to play toward (shared, or on a seat in play), and a multiplayer story needs a shared outcome, because its first thread groups every player on one. `storyStartProblem` holds the rule; `templateStartProblem(template, playerCount)` reads a template or setup reply (only the seats in play count) and `storyStateStartProblem(state, playerCount)` a created state. `StoryCreationService.createStoryFromTemplate` refuses a template story that breaks it with a 400, before any DB entry. `generateStoryState` retries a generated setup that breaks it once (a fresh sample of the same request) and otherwise fails through the setup-failure path.

**A setup that fails for good** (`server/src/stories/setupStatus.ts`). `generateStoryState` records the failure (`setup_failed`), deletes the story's DB entries and logs one line with the story id only (the error can quote the premise). `GET /stories/:id/status` then answers `failed`; a story neither stored nor being set up in this process (a restart mid-setup) answers `failed` / `setup_lost`, so no client waits forever. The client stops polling, drops the story's codes from local storage and shows "We couldn't create this story. Please try again." (`StorySetupFailed`) with Try again (the same premise and settings, sent through moderation and the rate limit again) and Back (the setup form, still filled in). A content-filter refusal is answered before anything is queued and keeps its own moderation notification. Template stories are created before the response (`ready`, or an HTTP error on the form); the same screen covers them should a poll ever report a failure. Invited players whose story failed get the game page's invalid-code error. The template editor's validation card (`validateTemplateIntegrity`, category `outcomes`) shows the problem for each player count it stops: an error when no allowed count can start, a warning when some can, and a warning for an outcome id held in more than one list (milestones land on one copy only: the first `Story.getOutcomeById` finds, shared first). Stories already running are not checked here.

**A turn that fails** (the queue's failure path, `BaseQueueProcessor.resendFailed`; `TURN_RESENDS` in `retryOnce.ts`, re-exported by `GameQueueProcessor.ts` and read by the eval's playthroughs, since 2026-09-30). A `moveStoryForward` whose writing throws (`handleProgression`: a plan unusable twice, a beat reply unusable, a call that failed through the chat model's re-sends) is queued once more, at the back of its game's queue, and runs `handleProgression` again from the same story: its own safeguards run again too. Only the writing is resent: once storing the written turn has begun it may be stored, so a failure storing or sending it is reported (`TurnDeliveryError`) but never written again, and the turn's images and pregeneration, which start after it is stored and sent, never fail it (logged only). The operation counts its `sends`, so it never loops; a warning names the operation and the error's class. A second failure takes the failure path: `operationError`, which `GameHandler` sends to every player in the game as "Unable to continue the story. Please try again." (its listener had been lost in 2025-05, so no failure reached anyone; a failed pregeneration tells no one, since the turn is written when it is played). A player's own failed choice or character selection reaches that player as its friendly line ("Unable to process your choice…", "Unable to save your character choice…"), and its pending operation is rejected with that line too, since `makeChoice`/`selectCharacter` and `websocket.ts` send the rejection's message on; the error's own text is logged only. The queue sends nothing a third time; a player's "Try again" does (below). Before, a failed turn was never sent again (the playthroughs' group stories, stuck for good). No other operation is resent.

**Trying a failed turn again** (since 2026-09-30). The game screen shows the failure where it was waiting (`TurnFailedNotice`, the ui `Notification` in its error style with no close button, `role="alert"`): in place of the next beat's spinner, of "Setting up the story..." (the first turn, or the other players still picking), below the latest beat when the player's own choice failed and its options are open again, or above the character selection's confirm button, which stops showing "Processing…" for the selection that failed (a new press locks it again while that request is on its way). The line is the server's; the button says "Try again". `turnFailureFrom` (`client/src/game/turnFailure.ts`) takes errors from the turn (`moveStoryForward`, `retry_turn`) and from the player's own choice or selection (queue or response), never an untyped or join-code error, and the notice stands until a state arrives in which the story moved on (a new beat, the player's choice or character stored; `stillFailed`), so when another player's retry works everyone's notice goes. "Try again" (`tryAgainRequest`, sent by `gameService.tryAgain`) sends what the story on screen is missing: the selection again while characters are picked, the player's choice again when it was never stored on that beat, else `retry_turn`; a choice it sends again shows as chosen, as a click on it does (`showChoiceSent`). The notice goes whenever the player sends something that answers it, "Try again" or their own choice or character through the game's controls (`clearTurnFailure` in `GamePage`'s handlers; `failureOnScreen`), so its "Try again" never sends the same again beside a send on its way; a rate-limited send brings it back. The queue records each player's choice on a beat, and each player's character, once (`choiceRecorded`, `characterRecorded` in `GameQueueProcessor`): `validateChoice` and `validateCharacterSelection` read the stored story, which lags the queue, so a copy sent while the first was queued or running passed and, recorded, queued the turn a second time. `GameHandler.retryTurn` queues `moveStoryForward` from the stored story only when it waits for its turn (every character picked, every choice in, `waitsForItsTurn`) and `GameQueueProcessor.isTurnOnItsWay` is false (no turn, choice or character selection queued or running, a resend included; `BaseQueueProcessor.hasUnfinished`), so any number of players pressing it queue one turn; otherwise it sends that player the story as stored. It counts against the `make_choice` rate limit; a limited retry brings the notice back. A player who arrives (a reload, a second device) at a story that waits for its turn with nothing on its way is told the same line (`tellIfTurnStuck`, after `verify_code`), and so is one who stays on the page while the connection comes back (a network drop, a server restart mid-turn): on every reconnect the client sends `rejoin_session` with the player's code, which nothing answered before 2026-09-30, so such a player got no more states and every choice or "Try again" failed ("Player not found") until a reload; now `GameHandler.rejoinGame` adds the new connection to the game and its room, sends the stored story and runs `tellIfTurnStuck` (rate-limited as `verify_code`, since it looks up a code). Still open: the other players' notices stay up while one player's retry is being written, until its beat arrives; and `recordChoice` and `recordCharacterSelection` still work from the story as it was when each request was checked, so two players choosing or picking within the same moment can leave only the second one stored (read in the code, not seen in play; the first player's options or character selection come back, with no notice).

**One retry** (`server/src/game/services/retryOnce.ts`). `withOneRetry(attempt, problemOf, what)` runs a model call, and when the result parses but has a problem, calls once more, passing the problem; a second problem throws `UnusableResultError` ("Failed to generate a usable <what>", the problem on `.problem`, never in the message). A call that fails outright is not retried there: the chat model already retries failed requests. The plan checks follow the same one-retry rule with their own flow, since a chapter length alone never fails the turn (above).
