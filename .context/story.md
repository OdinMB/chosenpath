### To manipulate and get information from the StoryState, use model classes

- Relevant model classes include Story.ts and ClientStateManager.ts, PlayerManager.ts, and ThreadManager.ts (all in shared/models directory).
- If these classes don't yet have a function to manipulate or get the required information from StoryState, add new functions to the classes.
- Don't add any complicated StoryState browsing and manipulation logic in other parts of the app.
- Keep story manipulation logic centralized in these domain models

### Checks and repairs on model replies

The game keeps what a model reply means, not only what matches an id exactly. Each repair is a `Repair` record (`server/src/game/services/textRepairs.ts`); `logRepairs` prints one `[LLM] repair` line per reply with the role, story id, turn and the count per kind (notes apart). The line carries no story text and no model-written ids; the records do, for tests and the eval, which checks replies after these repairs and counts them per kind (`.context/text-model-eval.md`, "Checks on what the game keeps").

**Beat replies** (`server/src/game/services/beatRepairs.ts`, `repairBeatReply`). `AIStoryGenerator.generateBeats` runs it on every reply, pregeneration siblings included, before `beatStep.apply`, so the beats are stored already repaired. `ChangeService` still applies exact ids only.

- Stat changes: a player stat in seat form (`player1_energy`, `player_player_energy`) is read as the plain id under that seat; a shared stat under a player moves to `shared`; in single player every player-stat change goes to player1. A player stat under `shared` in multiplayer, or a seat form under another player's group, is ambiguous and dropped; unknown stats are dropped. Both are counted.
- A `setString` value its stat's non-blank `possibleValues` don't mention is a note (`offLadderValue`); the change still applies.
- Facts: kept on `world`, a story element or an element created in the same reply. A fact filed under a stat, an outcome or a player slot becomes a world fact prefixed with the stat's name, the outcome's question or the character's name; any other id becomes an unprefixed world fact.
- Introductions of an element that neither exists nor is created in the reply are dropped.
- Milestones: the group comes from the outcome (shared first; an id held in two lists is noted). An unknown id is mapped only when exactly one ended thread's outcome has no milestone in the reply and exactly one milestone has an unknown id; otherwise it is dropped. On turns that may add milestones (`canAddMilestones` in `storyTextSteps.ts`: the ending, or a switch after the first beat), an ended thread (`Story.getResolvedThreadAnalysis()`) whose outcome got fewer milestones than threads that pushed it gets its planned `thread.milestone`; exploration threads record theirs too (`ThreadResolutionService.getMilestone`).
- Option types follow the player's phase (`expectedOptionType`): exploration at switches and in exploration threads, challenge in challenge and contest threads; the ending is untouched. A converted challenge option gets risk "normal", no bonuses, and base 0, or the fixed sacrifice / reward points.

**Switch and thread plans** (`server/src/game/services/planChecks.ts`). `AIStoryGenerator.generateSwitches` / `generateThreads` call the planner through `checkedSwitchPlan` / `checkedThreadPlan`: `checkSwitchPlan` / `checkThreadPlan` (pure) repair the reply where the fix is unambiguous and name what can't be used; a plan with a problem gets one more call with `Your previous plan could not be used: <problem>. Write the plan again.` appended to the prompt, and a second problem throws `UnusableResultError` into the turn's failure path. Pregenerated plans take the same path.

- Switches: a player stays in the first switch that lists them (a slot the story doesn't have is dropped, a switch left empty goes); a player in no switch is a problem. A flavor switch's directions are cleared; an unknown outcome or a blank question is a problem. Topic directions that are blank, under 12 letters or a piece of the reply's JSON (a field name followed by a quote, a colon or nothing; a quote followed by a colon) are dropped, and so are directions whose bracketed id-like words are all unknown; the first three stay, fewer than two is a problem. Directions naming two or more known outcomes, or none, are kept and noted (the one-outcome rule waits for its own field).
- Threads: a player stays in the first thread that lists them (so a single player keeps the first thread); a player in no thread is a problem. Duplicate ids get a numeric suffix. When every thread has the same number of steps, 2 to 4, the duration is taken from it; otherwise a problem. Problems too: an unknown outcome, a contest (side B filled) outside competitive and cooperative-competitive games or with an empty side A, and results of mixed kinds (the milestones and every step use one kind; contest results go with a filled side B, and only then). A contest's lowest slot goes on side A, the sides' results swapping with it. While the story has no thread plan (`Story.hasThreadAnalysis()`), a multiplayer plan must be one thread with every player, on a shared outcome when the story holds one (a contested shared one in a competitive game that holds one); the thread prompt's "MANDATORY FIRST THREAD REQUIREMENT" prints on the same condition.
- A story that holds no outcomes at all (one that started before the start check) skips every outcome rule; that is logged once per story per process. Repairs are logged as `[LLM] repair` lines (roles `switchAnalysis`, `threadAnalysis`); a plan that can't be used logs a warning without the problem, which names model-written ids.

**The roll.** `BeatResolutionService.calculateTotalPoints` counts only the first `MAX_STAT_MODIFIERS_PER_OPTION` (2) stat bonuses, each clamped to ±`MAX_STAT_MODIFIER_POINTS` (15, `core/config.ts`); the player's point breakdown shows the clamped values. Stored options keep what the model wrote, so the eval's bonus-range check still measures the model.

**Thread steps.** Before each thread beat, `ThreadResolutionService.resolveCurrentThreads` writes every thread's result for the beat just played. `ThreadManager.updateThreadResolution` puts it at that thread's own first unresolved step, so parallel threads each record step k on beat k and get their result and milestone on their last beat.

**Character selection.** `PlayerManager.setCharacterSelection` gives every player stat a value: a background stat the chosen background leaves out takes the stat's `initialValue`, or the template editor's default (`""`, `[]`, 50) when that is missing too. Stories already running are untouched.

**Story start** (`core/utils/outcomeReadiness.ts`). A story needs an outcome to play toward (shared, or on a seat in play), and a multiplayer story needs a shared outcome, because its first thread groups every player on one. `storyStartProblem` holds the rule; `templateStartProblem(template, playerCount)` reads a template or setup reply (only the seats in play count) and `storyStateStartProblem(state, playerCount)` a created state. `StoryCreationService.createStoryFromTemplate` refuses a template story that breaks it with a 400, before any DB entry. `generateStoryState` retries a generated setup that breaks it once (a fresh sample of the same request) and otherwise fails through the setup-failure path. The template editor's validation card (`validateTemplateIntegrity`, category `outcomes`) shows the problem for each player count it stops: an error when no allowed count can start, a warning when some can, and a warning for an outcome id held in more than one list (milestones land on one copy only: the first `Story.getOutcomeById` finds, shared first). Stories already running are not checked here.

**One retry** (`server/src/game/services/retryOnce.ts`). `withOneRetry(attempt, problemOf, what)` runs a model call, and when the result parses but has a problem, calls once more, passing the problem; a second problem throws `UnusableResultError` ("Failed to generate a usable <what>", the problem on `.problem`, never in the message). A call that fails outright is not retried there: the chat model already retries failed requests.
