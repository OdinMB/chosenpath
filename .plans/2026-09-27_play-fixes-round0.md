## Problem

Between a model's reply and the story, the game silently loses what the model wrote, and it shows the models state that is wrong or unreadable:

- **Turns.** A stat change written in the seat form the same reply uses for bonuses (`player1_energy`) is dropped with a console line (`ChangeService.ts:204-216`), so sacrifices go unpaid and rewards unpaid-out (4 of 12 gpt-4.1-mini and 5 of 12 Luna medium cases). Facts filed under a stat, outcome or "shared" vanish without a log (`ChangeService.ts:348-368`; 57 of 319 gpt-4.1-mini facts). Milestones with a wrong group or unknown id vanish without a log (`:108-147`). Exploration threads never record their milestone (`ThreadResolutionService.ts:288-314`). An option of the wrong type counts as nothing (`BeatResolutionService.ts:46-56`). Stat bonuses are never capped (`:297-320`; Luna breaks ±15 on 34 of 387 challenge options). A background that omits a background stat leaves the player without that stat, and every change to it is dropped (`PlayerManager.ts:289-303`).
- **Plans.** Nothing checks a switch or thread plan before it becomes the story (`AIStoryGenerator.ts:310-344`, `storyTextSteps.ts:147-190`): split chapters, junk directions, unknown outcomes, mixed kinds, a step list that disagrees with the length. The multiplayer first-thread rule prints only at turn 0 (`ThreadPromptService.ts:106`, `:175`), but the first thread plan runs at turn 1, so it never prints.
- **State text.** Opposites values read as a bare number (`StoryStatePromptService.ts:231`, `case "opposite"` against the type `"opposites"`). The planners' stat view has a dead "Narrative:" label (`:262-266`). The ended thread's header lacks its thread type (`:632`). Guideline lists and thread types run together with commas (`:119-127`, `:963-966`). The previous-thread-types list drops its first bullet (`:353-360`). An empty "SHARED OUTCOMES" header always prints (`:300-307`). A stat's possible values reach no prompt (`:245-298`). One flag has three names (`BeatPromptService.ts:149`, `:152` against `StoryStatePromptService.ts:294`).
- **Story start.** A template with no outcomes starts, and every plan then invents outcome ids (template `e401abf2`, 21 of 21 thread plans). A multiplayer story without a shared outcome starts, and its first grouped thread has nothing to push (3 of 70 multiplayer setups). The editor warns about neither, nor about an outcome id held in two lists.
- **Eval.** The checks read the raw reply, not what the game keeps (`outputChecks.ts:52-64`). The game-word check reads portrait tags (`textChecks.ts:138`; 107 of 119 hits). The hard cap is $30.

## What the documents got wrong, or left open (verified against the code)

1. **A step list shorter than the length** (turn doc A1, "inferred"): worse than stated. The thread never completes (`ThreadManager.ts:122-143`, `:294`), and the ending needs a completed thread (`:39-48`), so the story never ends. A longer list reaches its length but never sets the thread's result (`:306-309`), so no milestone.
2. **"Each direction must name exactly one known outcome"** (turn doc A1): the switch schema still asks for "the outcome or outcomes" (`core/types/switch.ts:75`), and stored GPT-6 directions name two or three ids routinely (`outputs/e96f16654e60a21bd48f`, `6b52e7c62240f8cd402e`). Enforcing one now would retry most GPT-6 switch plans. Round 0 drops only directions that name unknown ids and no known one; the one-outcome rule ships with A2's per-direction outcome field.
3. **Junk directions** (turn doc A1 "stray quote character"): the stored junk is `relationshipToOtherSwitches״: ` (U+05F4, not `"`), `title״: ` and `relationshipToOtherSwitches  ` (bare field name, trailing spaces). The rule below matches those forms.
4. **The fallback after a failed retry** (turn doc A1, UNSURE): superseded by the owner's rule. The turn fails through today's generation-error path; no invented fallback plan.
5. **"In competitive mode, without a contested shared outcome, the story doesn't start"** (turn doc A1): the template editor can neither create nor edit a contested outcome (setup doc B1.11: `OutcomeEditor.tsx:186-197`, `useOutcomeEditor.ts:56-136`). A block or an editor warning there would ask authors for something the editor cannot make. Deferred to the B1.11 editor fix. The thread check still requires a contested shared outcome for the first competitive thread when the story holds one.
6. **"B1's milestone code warns when an id is ambiguous, because the lookup returns the shared copy first"**: today the apply step never uses the lookup; it trusts the reply's group (`ChangeService.ts:108-147`). Once the group is derived from the outcome (TR-4), the lookup's shared-first order (`Story.ts:116-139`) decides. The warning stays.
7. **Clamp placement** (turn doc B3 row 1, "code also clamps"): clamping inside the reply repair would make the eval's `modifierRange` check always pass. The clamp goes where the roll is computed, so stored options stay as written, running stories are covered, the player's point breakdown shows the clamped value, and the check keeps measuring compliance.
8. **Option type repair "base 0"** (turn doc Appendix B1): for a sacrifice or reward option the option contract fixes the base at +30 or −30 (`core/types/beat.ts:53-59`). Only a normal option gets 0.
9. **"A world fact that starts with that outcome's name"** (turn doc Appendix B1): outcomes have no name. The prefix is the outcome's question.
10. **Introductions** (turn doc B1: "7 introductions in a turn whose text showed 2"): code can only catch unknown ids. Over-recording of known elements is not checkable and is not fixed here.
11. **Thread type in the header** (setup fix 4): the header at `:632` is shared with chapter turns. Round 0 adds the line only to a resolved thread, which is where after-thread adjustments are applied (switch beats, the ending, the switch planner). Chapter turns get it with B2's frame (round 1).
12. **Background stats** (setup doc B5.9): the setup document dropped it to "the code backlog" as a code fix. It is one here (TR-10).
13. **Not bugs today, dropped**: the unguarded `outcome.milestones.length` (`StoryStatePromptService.ts:318`, setup B9.3) cannot fail, because every path writes `milestones: []` (setup schema, `useOutcomeEditor.ts:33`, `usePlayerEditor.ts:169`); it matters only once setup proposal 9 stops writing the list. `setBoolean` (`core/types/change.ts:13`) has no stat type it could apply to (notes, stats.md §1.1); removing it changes the reply format.

## Decisions (owner-accepted defaults, and the defaults this plan sets)

- Stat bonuses: each clamped to ±15, and only the first two count.
- A planner reply that fails a check: repaired where the repair is unambiguous; otherwise one more call with the problem stated; if that fails too, the turn fails as today (the error propagates to the queue, as a failed model call does).
- A template-based story with no outcomes on the seats in play, or a multiplayer story without a shared outcome, does not start. The editor warns. A generated (custom) story that fails the same rule gets its setup retried once (a fresh sample, no prompt change), then fails through today's setup-failure path.
- Exploration threads record their milestone.
- Milestones: the group comes from the outcome. An unknown id is mapped when exactly one ended thread's outcome has no milestone in the reply and exactly one milestone has an unknown id; otherwise it is dropped and logged. An ended thread whose outcome got no milestone gets its planned milestone.
- A stat change in modifier (seat) form is normalised, not dropped.
- Facts filed under stat, outcome or player ids become world facts prefixed with the stat's name, the outcome's question or the character's name. Facts under "shared" or any other unknown id become unprefixed world facts. Logged.
- Stories already running on a template without outcomes skip the outcome checks, as today, logged once per story per process (an in-memory set of story ids, capped at 5,000).
- Contests: the lowest player slot in a contest is always on side A (two players: player1), with the milestone and step keys swapped to match.
- Possible values are shown in the turn's detailed stat view for every stat that has non-blank possible values.
- Directions naming two or more known outcomes, or none at all, are kept this round (see "got wrong" 2).
- Eval checks run on the normalised reply, and every repair is reported by kind, so the model's raw compliance stays visible.
